\chapter*{Введение}
\addcontentsline{toc}{chapter}{Введение}
Удалённый вызов процедур, реже Вызов удалённых процедур (от англ. Remote Procedure Call, RPC) - класс технологий, позволяющих компьютерным программам вызывать функции или процедуры в другом адресном пространстве (на удалённых компьютерах, либо в независимой сторонней системе на том же устройстве). Реализация RPC включает в себя два компонента: сетевой протокол для обмена данных и протокол сериализации объектов.\par
Средства удаленного вызова процедур предназначены для облегчения организации распределенных вычислений. Наибольшая эффективность использования RPC достигается в тех приложениях, в которых существует интерактивная связь между удаленными компонентами с небольшим временем ответов и относительно малым количеством передаваемых данных. Такие приложения называются RPC-ориентированными.\par
В данной работе будут рассмотрены одни из самых популярных реализаций RPC: gRPC и JSON-RPC.\\
\chapter{Обзор протоколов}
Рассмотрим подробнее указанные выше протоколы RPC.
\section{JSON-RPC}
JSON-RPC — протокол удалённого вызова процедур, использующий JSON для кодирования сообщений. Это очень простой протокол, определяющий только несколько типов данных и команд, стандартизированный JSON-RPC Working Group. У него нет какой-либо официальной реализации - все детали зависят от разработчика.
\section{gRPC}
gRPC - протокол RPC с открытым исходным кодом, разработанный компанией Google, в котором используется Protocol Buffers для сериализации данных (бинарный формат) и HTTP/2 в качестве протокола передачи данных.\\
\chapter{Сериализация данных}
Сериализация - процесс перевода какой-либо структуры данных в последовательность битов. При RPC-вызове происходит сериализация данных, передача их по сети, а затем десериализация данных в формат, понятный программному обеспечению вызывающей стороны.
\section{JSON-RPC}
В данном протоколе сериализация данных происходит в JSON - текстовый формат обмена данными. Его структура представляет собор пары ключ:значение, перечисленные через запятые. Массивы объектов представлены в квадратных скобках, а объекты - в фигурных скобках. Ниже можно увидеть пример json-файла.
\lstinputlisting[language=json, caption={Сериализованный в JSON объект}]{source/example.json}\par
Такой формат легко читается человеком и может редактироваться вручную. Однако размер сериализованных данных может быть гораздо больше бинарного формата сериализации. 
\section{gRPC}
gRPC использует Protocol Buffers - бинарный протокол сериализации данных. Протокол отличается маленьким размером сериализованных данных, однако читать и редактировать их человек не сможет. Также для сериализации и десериализации необходим специальный файл с описанием структуры данных, пример которого можно увидеть ниже.
\begin{lstlisting}[language=protobuf3, caption={Описание структур данных Protocol Buffers}]
message Empty{}

message RunMessage {
  string function_name = 1;
  repeated double param = 2;
}

message Point {
  double x = 1;
  double y = 2;
  double z = 3;
}

message PointBatch {
  repeated Point point = 1;
}
\end{lstlisting}\par
Описание структуры файла proto можно прочитать в документации:\\ https://developers.google.com/protocol-buffers/docs/proto3

\chapter{Передача данных}
Чаще всего самым узким по производительности местом в системе RPC является передача данных между клиентом и сервером. Рассмотрим какие протоколы используются для передачи данных в JSON-RPC и gRPC.
\section{JSON-RPC}
JSON-RPC имеет множество реализаций с использованием различных транспортных протоколов, однако наиболее популярные(т.е. постоянно развивающиеся) проекты используют протокол HTTP.\\
\section{gRPC}
По умолчанию в gRPC для передачи данных используется протокол HTTP/2, однако можно использовать любой другой протокол, даже разработанный самостоятельно.\par
HTTP/2 - вторая крупная версия сетевого протокола HTTP. Протокол HTTP/2 является бинарным. По сравнению с предыдущим стандартом изменены способы разбиения данных на фрагменты и транспортирования их между сервером и клиентом.\par
В HTTP/2 сервер имеет право послать то содержимое, которое ещё не было запрошено клиентом. Это позволит серверу сразу выслать дополнительные файлы, которые потребуются браузеру для отображения страниц, без необходимости анализа браузером основной страницы и запроса необходимых дополнений.\\
\chapter{Вызов процедур}
Рассмотрим как происходит удаленный вызов функций в рассматриваемых протоколах.
\section{JSON-RPC}
Формат сообщения-вызова задокументирован и представляет собой очень простую JSON-структуру, пример которой представлен ниже.
\begin{lstlisting}[language=json, caption={Формат сообщения-вызова JSON-RPC}]
--> {
     "jsonrpc": "2.0", 
     "method": 
     "subtract", 
     "params": {
         "subtrahend": 23, 
         "minuend": 42
     }, 
     "id": 3
    }
<-- {
     "jsonrpc": "2.0", 
     "result": 19, 
     "id": 3
    }
\end{lstlisting}
\section{gRPC}
Как и в случае с сериализацией, сообщения-вызовы в gRPC представляют собой компактную бинарную структуру, но требуют задокументированных в отдельном файле в специальном формате доступных для вызова функций. Пример описания функций представлен ниже.
\begin{lstlisting}[language=protobuf3, caption={Описание функций удаленного вызова gRPC}]
service ControlService {
  rpc StartTask (RunMessage) returns (stream PointBatch) {}
  rpc SuspendTask (Empty) returns (PointBatch) {}
  rpc ReadCurrentPoints (Empty) returns (PointBatch) {}
  rpc ResumeTask (Empty) returns (Empty) {}
  rpc TerminateTask (Empty) returns (PointBatch) {}
}
\end{lstlisting}\par
Подробнее о таком формате можно прочитать в документации:\\ https://grpc.io/docs/guides/concepts/
\section{Сравнение}
JSON-RPC использует простой формат сообщения, понятный человеку, из-за чего размер такого сообщения больше, чем у бинарного gRPC. Но, при этом, gRPC требует дополнительной документации функций удаленного вызова.
\chapter{Использование при разработке ПО}
Рассмотрим какие библиотеки для каких языков программирования существуют и насколько они удобны в использовании при построении собственной системы удаленного вызова процедур.
\section{JSON-RPC}
JSON-RPC лишь описывает протокол общения между клиентом и сервером, а всё остальное зависит от конкретной реализации, каких множество для большого числа языков программирования. Однако большинство даже самых популярных библиотек оставляют желать лучшего относительно удобства их использования, т.к. все они разработаны как домашние open source проекты отдельных программистов: слишком многие простые операции приходится делать вручную. Также стоит отметить, что не существует кроссязыковых библиотек JSON-RPC, из чего следуют сложности при разработке проекта на нескольких языках.
\section{gRPC}
gRPC представляет собой библиотеку для наиболее популярных языков программирования, в каждом из которых сохраняются все концепции gRPC в том или ином виде. Из файла .proto с описанием интерфейса и формата сообщений может быть сгенерирован код RPC-системы для любого поддерживаемого языка. Это позволяет легко разрабатывать кроссязыковые проекты.
\chapter*{Заключение}
\addcontentsline{toc}{chapter}{Заключение}
Таким образом, были рассмотрены протоколы удаленного вызова процедур gRPC и JSON-RPC и описаны их достоинства и недостатки.\par
JSON-RPC прост в реализации и его сообщения могут быть легко прочитаны и отредактированы человеком, но размер сериализованных данных оставляет желать лучшего. Это может стать узким местом системы удаленного вызова процедур, т.к. скорость передачи данных обычно невысока по сравнению со скоростью работы жесткого диска и процессора.\par
gRPC использует бинарный Protocol Buffers, благодаря чему размер сериализованных данных очень мал по сравнению с текстовой сериализацией. Но это требует описания сервиса RPC в специальном формате. Также стоит отметить, что gRPC невозможно (либо очень сложно) использовать с неподдерживаемыми библиотекой языками программирования.
