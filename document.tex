\chapter*{Введение}
\addcontentsline{toc}{chapter}{Введение}
Удалённый вызов процедур, реже Вызов удалённых процедур (от англ. \EN{Remote Procedure Call, RPC}) - класс технологий, позволяющих компьютерным программам вызывать функции или процедуры в другом адресном пространстве (на удалённых компьютерах, либо в независимой сторонней системе на том же устройстве). Реализация RPC включает в себя два компонента: сетевой протокол для обмена данных и протокол сериализации объектов.

Средства удаленного вызова процедур предназначены для облегчения организации распределенных вычислений. Наибольшая эффективность использования RPC достигается в тех приложениях, в которых существует интерактивная связь между удаленными компонентами с небольшим временем ответов и относительно малым количеством передаваемых данных. Такие приложения называются RPC\hyp{}ориентированными.

В данной работе будут рассмотрены одни из самых популярных реализаций RPC: gRPC и JSON\hyp{}RPC.
\chapter{Обзор протоколов}
Рассмотрим подробнее указанные выше протоколы RPC.
\section{JSON-RPC}
JSON-RPC — протокол удалённого вызова процедур, использующий JSON для кодирования сообщений. Это очень простой протокол, определяющий только несколько типов данных и команд, стандартизированный JSON-RPC Working Group. У него нет какой-либо официальной реализации - все детали зависят от разработчика.
\section{gRPC}
gRPC - протокол RPC с открытым исходным кодом, разработанный компанией Google, в котором используется Protocol Buffers для сериализации данных (бинарный формат) и HTTP/2 в качестве протокола передачи данных. Код протокола является открытым, выложен на github и любой может его посмотреть и предложить свои изменения.
\chapter{Сериализация данных}
Сериализация - процесс перевода какой-либо структуры данных в последовательность битов. При RPC-вызове происходит сериализация данных, передача их по сети, а затем десериализация данных в формат, понятный программному обеспечению вызывающей стороны. Сериализация необходима из-за того, что нет никаких гарантий бинарной совместимости (ABI) сервера и клиента.
\section{JSON-RPC}
В данном протоколе сериализация данных происходит в JSON - текстовый формат обмена данными. Он основан на подмножестве языка программирования JavaScript, определенного в стандарте ECMA-262 3rd Edition (December 1999). Его структура представляет собор пары \textit{ключ:значение}, перечисленные через запятые. Массивы объектов представлены в квадратных скобках, а объекты - в фигурных скобках.

\lstinputlisting[language=json, caption={Сериализованный в JSON объект}]{source/example.json}

Такой формат легко читается человеком и может редактироваться вручную. Однако размер сериализованных данных может быть гораздо больше бинарного формата сериализации из-за хранения любых значений в виде текста и обязательного аннотирования полей структуры. JSON-сериализация поддерживается многими языками "из коробки", что упрощает работу с ним.
\section{gRPC}
gRPC использует Protocol Buffers - бинарный протокол сериализации данных, т.е. данные представляют собой не читабельный для человека набор байт. Для его работы необходимо описать структуру сериализуемых данных на специальном декларативном языке proto3. Язык позволяет определять структуры (message), перечисления (enum), множество числовых типов разного размера (целые и с плавающей запятой), строки, массивы (поля repeated), ассоциативные массивы (map) и многое другое. Для каждого из полей задается числовой тег, обычно соответствующий порядковому номеру.

\lstinputlisting[language=protobuf3, caption={Описание структур данных Protocol Buffers}]{source/example.proto}

Как Protocol Buffers сериализует данные? Числовые типы с плавающей или фиксированной запятой не кодируются и сериализуются как есть. Структуры сериализуются путем последовательной сериализации каждого поля с заголовком в виде тега и типа поля.Все целочисленные типы кодируются алгоритмом ZigZag в специальный формат variant, в котором количество памяти, занимаемое числом, зависит от самого числа. Его максимальный размер составляет 10 байт. ZigZag кодирует число, нумеруя их по порядку, чередуя положительные и отрицательные. Таким образом, четный номер - положительное число, а нечетный - отрицательное.

\begin{table}[H]
  \centering
  \begin{tabular}{|l|l|}
  \hline
  Оригинал    & ZigZag     \\ \hline
  0           & 0          \\ \hline
  -1          & 1          \\ \hline
  1           & 2          \\ \hline
  -2          & 3          \\ \hline
  2147483647  & 4294967294 \\ \hline
  -2147483648 & 4294967295 \\ \hline
  \end{tabular}
  \caption{Кодирование числа с помощью ZigZag}
\end{table}

Из такого файла имеется возможность сгенерировать исходный код для любого из поддерживаемых языков (C++, C\#, Java, Python, Go и т.д.), в которых описанные структуры будут представлены в виде классов с методами get и set для каждого из полей. Также стоит отметить, что для совместимости между различными системами имеется возможность конвертации как из protobuf\hyp{}структуры в JSON, так и наоборот.
Полное описание языка proto3 можно прочитать в документации:\\ https://developers.google.com/protocol-buffers/docs/proto3

\chapter{Передача данных}
Чаще всего самым узким по производительности местом в системе RPC является передача данных между клиентом и сервером. Рассмотрим какие протоколы используются для передачи данных в JSON-RPC и gRPC.
\section{JSON-RPC}
JSON-RPC имеет множество реализаций с использованием различных транспортных протоколов, однако наиболее популярные (постоянно развивающиеся) проекты используют протокол HTTP. В данном протоколе данные передаются в текстовом виде, что не безопасно и из-за чего размер пакета может быть довольно большим.

\end{figure}
\section{gRPC}
По умолчанию в gRPC для передачи данных используется протокол HTTP/2, однако можно использовать любой другой протокол, даже разработанный самостоятельно.

HTTP/2 - вторая крупная версия сетевого протокола HTTP. Протокол HTTP/2 является бинарным, что позволяет уменьшит размер пакета по сравнению с HTTP/1. Также изменены способы разбиения данных на фрагменты и транспортирования их между сервером и клиентом, что ускоряет передачу данных.
\begin{figure}[H]
	\center{\includegraphics[width=1\linewidth]{http2}}
	\caption{Протокол HTTP/2}
\end{figure}
В HTTP/2 сервер имеет право послать то содержимое, которое ещё не было запрошено клиентом. Это позволит серверу сразу выслать дополнительные файлы, которые потребуются браузеру для отображения страниц, без необходимости анализа браузером основной страницы и запроса необходимых дополнений.

gRPC также обладает возможностью включить TLS-шифрование для передаваемых пакетов. TLS даёт возможность клиент-серверным приложениям осуществлять связь в сети таким образом, что нельзя производить прослушивание пакетов и осуществить несанкционированный доступ.
\chapter{Диспетчеризация вызовов}
В интерфейсе RPC-сервера может содержаться больше одной функции, поэтому необходима диспетчеризация вызовов: какую функцию должен вызвать сервер?
\section{JSON-RPC}
Формат сообщения-вызова задокументирован и представляет собой очень простую JSON-структуру. Запрос состоит из полей: версия протокола, название функции, передаваемые параметры, идентификатор вызова. Ответ состоит из версии, собственно результата и идентификатора вызова. Все детали реализации диспетчеризации ложатся на плечи разработчика, стандарт документирует лишь формат сообщения.

\section{gRPC}
Как и в случае с сериализацией, сообщения-вызовы в gRPC представляют собой компактную бинарную структуру, но требуют задокументированных в отдельном файле в специальном формате доступных для вызова функций. Описание функции представляет из себя следующий шаблон:
\begin{verbatim}
  rpc имя_функции ([[stream] параметр, ...]) 
    returns ([[stream] возвращаемое_значение]) {}
\end{verbatim}
Параметры и возвращаемое значение представляют собой структуры Protocol Buffer, рассмотренные ранее. gRPC также позволяет осуществлять потоковую передачу параметров или результата вызова функции, для этого используется ключевое слово \textit{stream} в описании параметра или возвращаемого значения.
\lstinputlisting[language=protobuf3, caption={Описание интерфейса}]{source/grpc.proto}
Подробнее о таком формате можно прочитать в документации:\\ https://grpc.io/docs/guides/concepts/
\section{Сравнение}
JSON-RPC использует простой формат сообщения, понятный человеку, из-за чего размер такого сообщения больше, чем у бинарного gRPC. Но, при этом, gRPC требует дополнительной документации функций удаленного вызова.
\chapter{Использование при разработке ПО}
Рассмотрим какие библиотеки для каких языков программирования существуют и насколько они удобны в использовании при построении собственной системы удаленного вызова процедур.
\section{JSON-RPC}
JSON-RPC лишь описывает протокол общения между клиентом и сервером, а всё остальное зависит от конкретной реализации, каких множество для большого числа языков программирования. Однако большинство даже самых популярных библиотек оставляют желать лучшего относительно удобства их использования, т.к. все они разработаны как домашние open source проекты отдельных программистов: слишком многие простые операции приходится делать вручную. Также стоит отметить, что не существует кроссязыковых библиотек JSON-RPC, из чего следуют сложности при разработке проекта на нескольких языках.
\section{gRPC}
gRPC представляет собой библиотеку для наиболее популярных языков программирования, в каждом из которых сохраняются все концепции gRPC в том или ином виде. Из файла .proto с описанием интерфейса и формата сообщений может быть сгенерирован код RPC-системы для любого поддерживаемого языка. Это позволяет легко разрабатывать кроссязыковые проекты.
\chapter*{Заключение}
\addcontentsline{toc}{chapter}{Заключение}
Таким образом, были рассмотрены протоколы удаленного вызова процедур gRPC и JSON-RPC и описаны их достоинства и недостатки.

JSON-RPC прост в реализации и его сообщения могут быть легко прочитаны и отредактированы человеком, но размер сериализованных данных оставляет желать лучшего. Это может стать узким местом системы удаленного вызова процедур, т.к. скорость передачи данных обычно невысока по сравнению со скоростью работы жесткого диска и процессора.

gRPC использует бинарный Protocol Buffers, благодаря чему размер сериализованных данных очень мал по сравнению с текстовой сериализацией. Но это требует описания сервиса RPC в специальном формате. Также стоит отметить, что gRPC невозможно (либо очень сложно) использовать с неподдерживаемыми библиотекой языками программирования.
