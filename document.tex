КЛЮЧЕВЫЕ СЛОВА: КЛАСТЕР, УДАЛЕННЫЙ ВЫЗОВ ПРОЦЕДУР, ПАРАЛЛЕЛЬНЫЕ ВЫЧИСЛЕНИЯ, \EN{MPI, OPENMP}, ЗАДАЧА ДИРИХЛЕ, УРАВНЕНИЕ ПУАССОНА, МЕЖПРОЦЕССНОЕ ВЗАИМОДЕЙСТВИЕ.

Тема выпускной квалификационной работы: <<Система распределения вычислений на высокопроизводительном кластере при решении задач численного моделирования>>.

Данная работа посвящена исследованию путей повышения эффективности вычислений при решении задач численного моделирования на высокопроизводительном кластере. Задачи, которые решались в ходе исследования:
\begin{enumerate}
  \item Исследовать существующие методы и алгоритмы распределения вычислений на высокопроизводительном кластере.
  \item Разработать эффективный параллельный алгоритм решения задачи численного моделирования на примере задачи Дирихле.
  \item Провести экспериментальные исследования разработанного решения со сравнительным анализом результатов для различных реализаций распределения.
  \item Выполнить программную реализацию разработанного алгоритма и основанной на нём системы распределения вычислений, выполняющей все этапы – от ввода данных до вывода результата.
\end{enumerate}
В ходе данной работы было проведено исследование путей повышения эффективности вычислений при решении задач численного моделирования на высокопроизводительном кластере и была реализована полноценная система распределенных вычислений.

Была решена задача Дирихле уравнения Пуассона с помощью метода конечных разностей. Получившаяся система линейных алгебраических уравнений была решена с помощью метода Гаусса-Зейделя, параллельная реализация которого была разработана с совместным использованием технологий OpenMP и MPI. Для сравнения производительности были построены еще три версии алгоритма: последовательный, только OpenMP и только MPI.

Также был реализован сервер удаленного вызова процедур с использованием библиотеки gRPC. Для коммуникации между численной моделью и сервером была использована технология межроцессного взаимодействия, которая была реализована на основе использования неименованного канала с применением библиотек Boost.Process и Boost.Asio.

В качестве интерфейса пользователя было разработано кроссплатформенное графическое приложение на языке Python с использованием библиотек Qt, matplotlib и gRPC.

  The subject of the graduate qualification work is "The distribution system of calculations on a high-performance cluster in solving problems of numerical simulation".

  The given work is devoted to studying of ways to increase the efficiency of calculations in solving problems of numerical modeling on a high-performance cluster. The research set the following goals:

  \begin{enumerate}
    \item Explore existing methods and algorithms for distributing computations on a high-performance cluster.
    \item Develop an effective parallel algorithm for solving the problem of numerical simulation using the Dirichlet problem as an example.
    \item Conduct experimental studies of the developed solution with a comparative analysis of the results for various distribution implementations.
    \item Execute the software implementation of the developed algorithm and the calculation distribution system based on it, which performs all stages - from data input to output.
  \end{enumerate}

  In the course of this work, a study was conducted of ways to increase the efficiency of calculations in solving problems of numerical modeling on a high-performance cluster and a complete system of distributed computing was implemented.

  The Dirichlet problem of the Poisson equation was solved using the finite difference method. The resulting system of linear algebraic equations was solved using the Gauss-Seidel method, a parallel implementation of which was developed with the combined use of OpenMP and MPI technologies. To compare performance, three more versions of the algorithm were built: serial, only OpenMP and only MPI.

  A remote procedure call server was also implemented using the gRPC library. For communication between the numerical model and the server, the interprocess communication technology was used, which was implemented using an unnamed channel using the Boost.Process and Boost.Asio libraries.

  As a user interface, a cross-platform graphical application in Python was developed using the Qt, matplotlib and gRPC libraries.

Согласно закону Мура, количество транзисторов, размещаемых на кристалле интегральной схемы, удваивается каждые 24 месяца. Из этих изменений следует повышение частоты центрального процессора компьютера и, соответственно, его вычислительной мощи. Однако в последние годы закон Мура перестал действовать из-за атомарной природы вещества и ограничения скорости света. Производители ЦПУ столкнулись с непреодолимыми физическими ограничениями. Но скорость вычислений можно повысить и другим способом -- заставить работать вместе несколько процессоров. Такие объединения называются кластерами или суперкомпьютерами. Это огромные вычислительные машины, объединяющие множество процессоров.

Но такие устройства требуют совершенно другого подхода к разработке -- параллельного программирования. Этот подход подразумевает под собой, что максимальное количество частей программы будут исполняться параллельно. Действительно, это ускоряет вычисления, но сложность таких программ существенно возрастает.

Цель данной работы -- исследование путей повышения эффективности вычислений при решении задач численного моделирования на высокопроизводительном кластере.

\section{Параллельное решение задачи численного моделирования}
\subsection{Постановка задачи}
В качестве решаемой задачи в данной работе была выбрана задача Дирихле для уравнения Пуассона. Уравнение Пуассона - эллиптическое дифференциальное уравнение в частных производных, описывающее обширный класс объектов: электростатическое поле, поле давления, адиабатный процесс и т.д. Уравнение имеет вид
\begin{equation*}
  \Delta\phi=f,
\end{equation*}
где $\Delta$ - оператор Лапласа,

$f$ - вещественная или комплексная функция на некотором многообразии.

Конкретизируем задачу. Тогда уравнение принимает вид:
\begin{equation*}
  \begin{cases}
    \dfrac{\delta^2u}{\delta x^2}+\dfrac{\delta^2u}{\delta y^2}=f(x,y), &\text{$(x,y) \in D$}\\
    u(x,y)=g(x,y), &\text{$(x,y) \in D^0$}
  \end{cases},
\end{equation*}
где $u=u(x,y)$ - искомая функция,

$D$ - область определения,

$g(x,y)$ - краевые условия,

$D^0$ - граница области $D$,

$f=f(x,y)$ - заданная функция.\\
За область определения $D$ примем единичный квадрат
\begin{equation*}
  D=\{(x,y) \in D: 0 \le x,y \le 1\}
\end{equation*}
Дискретизируем систему, применив метод конечных разностей~\cite{1ustinov_math}, также называемый методом сеток (\cref{grid_method}).
\begin{equation*}
  \begin{cases}
    D_h=\{(x_i,y_j): x_i=ih, y_j=jh, 0 \le i,j \le N+1\}\\
    h=1/(N+1)
  \end{cases},
\end{equation*}
где $N$ - количество узлов по каждой из координат области $D$. 
\begin{figure}[h]
	\center{\includegraphics[width=0.5\linewidth]{grid_method}}
  \caption{Метод сеток}
  \label{grid_method}
\end{figure}

Обозначим аппроксимацию функции $u(x,y)$ в точке $(x_i, y_i)$ через $u_{ij}$. Тогда уравнение Пуассона в конечно-разностной форме принимает вид:
\begin{equation*}
  \dfrac{u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}-4u_{ij}}{h^2}=f_{ij}
\end{equation*}
Относительно $u_{ij}$:
\begin{equation*}
  u_{ij}=\dfrac{u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}-h^2f_{ij}}{4}
\end{equation*}
Таким образом, задача сводится к решению системы линейных алгебраических уравнений
\subsection{Методы решения СЛАУ}
Рассмотрим методы решения СЛАУ~\cite{1ustinov_math} и возможность их параллельной реализации.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. Метод Якоби}
Применив метод Якоби к описанной выше задаче получим:
\begin{equation*}
  u^k_{ij}=\dfrac{u^{(k-1)}_{i-1,j}+u^{(k-1)}_{i+1,j}+u^{(k-1)}_{i,j-1}+u^{(k-1)}_{i,j+1}-h^2f_{ij}}{4}
\end{equation*}
Таким образом, для нахождения $u^(k)_{ij}$ нам необходимо знать значение функции в соседних узлах на предыдущей итерации. Такой подход очень легко поддается распараллеливанию. Всего лишь необходимо синхронизировать окончание итерации всеми потоками исполнения и хранить матрицу значений предыдущей итерации.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. Метод Гаусса-Зейделя}
Главное отличие метода Гаусса-Зейделя от метода Якоби в том, что значения текущей итерации используются сразу же по мере получения, что увеличивает его скорость сходимости. Поэтому уравнение принимает вид:
\begin{equation*}
  u^k_{ij}=\dfrac{u^{(k)}_{i-1,j}+u^{(k-1)}_{i+1,j}+u^{(k)}_{i,j-1}+u^{(k-1)}_{i,j+1}-h^2f_{ij}}{4}
\end{equation*}

Для расчета очередного узла необходимы значения функции на текущей итерации слева и сверху и значения предыдущей итерации справа и снизу. Параллельный алгоритм для данного метода можно представить в виде волны (\cref{wave}): сначала производится расчет значения функции в левом верхнем узле, затем параллельно рассчитываются узлы справа и снизу и так далее. Максимум одновременно работающих потоков будет равен размерности сетки.

  \caption{Волновой алгоритм}

\end{figure}

\subsection{Средства реализации параллельного алгоритма}
В качестве языка программирования был выбран C++ как один из самых производительных, что важно для сложных вычислений. В реализации алгоритма необходимо будет воспользоваться такими объектами линейной алгебры, как матрицы и вектора. Средствами стандартной библиотеки их можно представить разве что в виде двумерного массива, использование которого требует выполнение всех примитивных операций вручную, что увеличивает вероятность возникновения ошибок реализации. Здесь на помощь приходит библиотека линейной алгебры Boost.uBLAS~\cite{3boost}, предоставляющая простой и понятный интерфейс для большого числа операций. Пример использования библиотеки представлен на \cref{ublas}.
\begin{figure}[H]

Помимо линейной алгебры, необходимо реализовать параллельность. Существует множество различных способов реализовать параллельный алгоритм. Все их можно разделить на два класса: для систем с общей памятью и для систем с распределенной памятью. Рассмотрим по порядку оба класса и определим границы их применимости. 
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. Системы с общей памятью}
В таких системах все процессоры обращаются к общей для всех процессоров памяти. Примером такой системы может послужить любой персональный компьютер: все ядра процессора обращаются к общей оперативной памяти и могут читать/писать в одни и те же ячейки памяти. Рассмотрим способы реализации параллельных алгоритмов в таких системах.

Очевидный способ - использовать стандартную библиотеку языка программирования C++~\cite{1cpp_base}. Библиотека thread предоставляет возможность создания потоков с помощью класса std::thread и асинхронного вызова функций с помощью std::async.

Другим способом является технология \EN{OpenMP (Open Multi\hyp{}Processing)} — открытый стандарт для распараллеливания программ на языках C, C++ и Фортран\cite{2openmp}. Стандарт предоставляет описание директив компилятора, библиотечных процедур и переменных окружения, которые предназначены для программирования многопоточных приложений на многопроцессорных системах с общей памятью. 
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. Системы с распределенной памятью}
Для таких систем характерно наличие собственной приватной памяти у каждого процессора. Примером такой системы может послужить суперкомпьютер: несколько отдельных компьютеров, соединенных в высокоскоростную сеть. Для обмена информации между процессорами используется специальный интерфейс -- \EN{Message Passing Interface} (MPI, интерфейс передачи сообщений)~\cite{2mpi}. Интерфейс позволяет передавать сообщения между процессорами, а разделение работы происходит посредством определения номера процессора и исполнения соответствующего кода. На \cref{mpi_sample} можно увидеть пример работы с таким интерфейсом.

\begin{figure}[h]
  \lstinputlisting[language=c++]{source/mpi.cpp}
  \caption{Листинг. Пример MPI-программы}
  \label{mpi_sample}
\end{figure}

Передача значения функции в узле другому процессору очень затратная операция, особенно если сеть, объединяющая процессоры, имеют высокую задержку. Таким образом, расчет каждым процессором узла по одному может оказаться даже медленнее последовательного алгоритма. Чтобы избежать этого, можно увеличить количество кода, выполняемого последовательно, и реализовать блочно-волновую схему (\cref{wave_block}). В такой схеме каждый процессор будет рассчитывать значения функции в целом блоке узлов, а затем передавать свои крайние строки другому процессору.

	\center{\includegraphics[width=0.5\linewidth]{wave_block}}
  \caption{Блочно-волновой алгоритм}
  \label{wave_block}
\end{figure}

Библиотека \EN{MPI} предоставляет лишь примитивный интерфейс\\языка программирования \EN{C}, и многие вещи приходится делать вручную: инициализация и деинициализация окружения, передача сложных структур данных и прочее. Из-за этого сложность больших программ увеличивается, и вероятность появления труднонаходимых багов повышается. Поэтому для своей реализации алгоритма Гаусса-Зейделя я буду использовать библиотеку \EN{Boost.MPI} -- C++ обертку над MPI. Благодаря ей многие вещи становится гораздо проще написать (\cref{boost_mpi}).

Самое главное достоинство Boost.MPI в том, что она позволяет использовать библиотеку \EN{Boost.Serialization} для отправки сложных структур данных. Чтобы структура стала сериализуемой достаточно определить у нее метод \EN{serialize}, все остальное произойдет автоматически. Структуры из упомянутой ранее библиотеки \EN{Boost.uBLAS}, такие как матрицы и вектора, уже имеют этот метод, что сильно упрощает процедуру обмена строк, необходимую для реализации алгоритма.

\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. Смешанные системы}
Рассмотрим подробнее архитектуру суперкомпьютера. Компьютеры объединены в систему с разделенной памятью с помощью сети. Каждый компьютер в такой сети представляет из себя многоядерный процессор, т.е. систему с общей памятью. Таким образом, в общем случае, суперкомпьютер является смешанной системой: система с разделенной памятью с подсистемами с общей памятью. В таких условиях использование OpenMP возможно только в рамках одной подсистемы, а использование MPI влечет за собой накладные расходы из-за пересылок сообщений внутри одной подсистемы между ядрами одного процессора.

Для увеличения производительности алгоритма возможно совместить технологии OpenMP и MPI. В таком случае каждый блок блочно-волной схемы будет рассчитываться в одной подсистеме, что позволит нам сделать MPI, а внутри подсистемы будет происходить параллелизация по потокам с помощью OpenMP и волновой схемы (\cref{cluster_arch}).

\section{Удаленный вызов процедур}
Удалённый вызов процедур, реже Вызов удалённых процедур (от англ. \EN{Remote Procedure Call, RPC}) - класс технологий, позволяющих компьютерным программам вызывать функции или процедуры в другом адресном пространстве (на удалённых компьютерах, либо в независимой сторонней системе на том же устройстве). Реализация RPC включает в себя два компонента: сетевой протокол для обмена данных и протокол сериализации объектов.

С использованием данной технологии возможно разработать управляющий модуль для написанной ранее программы, реализующей алгоритм Гаусса\hyp{}Зейделя. Рассмотрим, как работает данная технология через сравнение двух наиболее известных на сегодняшний день реализаций: gRPC и JSON-RPC, и выберем, какую следует использовать в данной работе.
\subsection{Обзор протоколов}
Рассмотрим подробнее указанные выше протоколы RPC.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. JSON-RPC}
JSON-RPC — протокол удалённого вызова процедур, использующий формат JSON для кодирования сообщений. Это очень простой протокол, определяющий только несколько типов данных и команд, стандартизированный JSON-RPC Working Group~\cite{3jsonrpc}. У него нет какой-либо официальной реализации - все детали зависят от разработчика.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. gRPC}
gRPC - протокол RPC с открытым исходным кодом~\cite{3grpchabr}, разработанный компанией Google, в котором используется Protocol Buffers для сериализации данных (бинарный формат) и HTTP/2 в качестве протокола передачи данных. Код протокола является открытым, выложен на github и любой может его посмотреть и предложить свои изменения.
\subsection{Сериализация данных}
Сериализация - процесс перевода какой-либо структуры данных в последовательность битов. При RPC-вызове происходит сериализация данных, передача их по сети, а затем десериализация данных в формат, понятный программному обеспечению вызывающей стороны. Сериализация необходима из-за того, что нет никаких гарантий бинарной совместимости (ABI) сервера и клиента.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. JSON-RPC}
В данном протоколе сериализация данных происходит в JSON -- текстовый формат обмена данными. Пример такого формата можно увидеть на \cref{json}. Он основан на подмножестве языка программирования JavaScript, определенного в стандарте \EN{ECMA-262 3rd Edition (December 1999)}. Его структура представляет собор пары \textit{ключ:значение}, перечисленные через запятые. Массивы объектов представлены в квадратных скобках, а объекты - в фигурных скобках.

\begin{figure}[H]
  \lstinputlisting[language=json]{source/example.json}
  \caption{Листинг. Сериализованный в JSON объект}
  \label{json}
\end{figure}

Такой формат легко читается человеком и может редактироваться вручную. Однако размер сериализованных данных может быть гораздо больше бинарного формата сериализации из-за хранения любых значений в виде текста и обязательного аннотирования полей структуры. JSON-сериализация поддерживается многими языками <<из коробки>>, что упрощает работу с ним.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. gRPC}
gRPC использует Protocol Buffers -- бинарный протокол сериализации данных, т.е. данные представляют собой не читабельный для человека набор байт. Для его работы необходимо описать структуру сериализуемых данных на специальном декларативном языке proto3. Язык позволяет определять структуры (message), перечисления (enum), множество числовых типов разного размера (целые и с плавающей запятой), строки, массивы (поля repeated), ассоциативные массивы (map) и многое другое. Для каждого из полей задается числовой тег, обычно соответствующий порядковому номеру (\cref{grpc}).
\FloatBarrier
\begin{figure}[h]
  \lstinputlisting[language=protobuf3]{source/example.proto}
  \caption{Листинг. Описание структур данных Protocol Buffers}
  \label{grpc}
\end{figure}

Как Protocol Buffers сериализует данные? Числовые типы с плавающей или фиксированной запятой не кодируются и сериализуются как есть. Структуры сериализуются путем последовательной сериализации каждого поля с заголовком в виде тега и типа поля.Все целочисленные типы кодируются алгоритмом ZigZag в специальный формат variant, в котором количество памяти, занимаемое числом, зависит от самого числа (\cref{zigzag}). Его максимальный размер составляет 10 байт. ZigZag кодирует число, нумеруя их по порядку, чередуя положительные и отрицательные. Таким образом, четный номер - положительное число, а нечетный - отрицательное.

\begin{table}[h]
  \centering
  \caption{}
  \label{zigzag}
  \begin{subtable}[t]{\linewidth}
    \centering
    \caption*{Кодирование числа с помощью ZigZag}
    \begin{tabular}{|l|l|}
      \hline
      Оригинал    & ZigZag     \\ \hline
      0           & 0          \\ \hline
      -1          & 1          \\ \hline
      1           & 2          \\ \hline
      -2          & 3          \\ \hline
      2147483647  & 4294967294 \\ \hline
      -2147483648 & 4294967295 \\ \hline
    \end{tabular}
  \end{subtable}
\end{table}

Из такого файла имеется возможность сгенерировать исходный код для любого из поддерживаемых языков (C++, C\#, Java, Python, Go и т.д.), в которых описанные структуры будут представлены в виде классов с методами get и set для каждого из полей. Также стоит отметить, что для совместимости между различными системами имеется возможность конвертации как из protobuf\hyp{}структуры в JSON, так и наоборот.
Полное описание языка proto3 можно прочитать в документации~\cite{3protobuf}.

Какой же из двух форматов быстрее и компактнее сериализует данные? На \cref{proto_vs_json} приведены сравнительные графики производительности описанных выше протоколов.

Как можно увидеть из графика (см.\cref{proto_vs_json}), скорость сериализации по протоколу \EN{Protocol Buffers} в несколько раз выше JSON, однако десериализация может оказаться медленнее из-за сложного формата упаковки данных. Это компенсируется размером сериализованных данных, например, 565 байт против 2462.
\subsection{Передача данных}
Чаще всего самым узким по производительности местом в системе RPC является передача данных между клиентом и сервером. Рассмотрим какие протоколы используются для передачи данных в JSON-RPC и gRPC.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. JSON-RPC}
JSON-RPC имеет множество реализаций с использованием различных протоколов передачи данных, однако наиболее популярные (постоянно развивающиеся) проекты используют протокол HTTP. В данном протоколе данные передаются в текстовом виде (\cref{http}), что не безопасно и из-за чего размер пакета может быть довольно большим.

\end{figure}
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. gRPC}
По умолчанию в gRPC для передачи данных используется протокол HTTP версии 2, однако можно использовать любой другой протокол, даже разработанный самостоятельно.

HTTP/2 - вторая крупная версия сетевого протокола HTTP. Протокол является бинарным, что позволяет уменьшит размер пакета по сравнению с HTTP/1. Также изменены способы разбиения данных на фрагменты и транспортирования их между сервером и клиентом, что ускоряет передачу данных. Пример работы протокола представлен на \cref{http2}.

В HTTP/2 сервер имеет право послать то содержимое, которое ещё не было запрошено клиентом. Это позволит серверу сразу выслать дополнительные файлы, которые потребуются браузеру для отображения страниц, без необходимости анализа браузером основной страницы и запроса необходимых дополнений~\cite{3http}.

\FloatBarrier
gRPC также обладает возможностью включить TLS-шифрование для передаваемых пакетов. TLS даёт возможность клиент-серверным приложениям осуществлять связь в сети таким образом, что нельзя производить прослушивание пакетов и осуществить несанкционированный доступ.

\subsection{Использование при разработке ПО}
Рассмотрим какие библиотеки для каких языков программирования существуют и насколько они удобны в использовании при построении собственной системы удаленного вызова процедур. В качестве примеров будем рассматривать примеры на языке программирования Python, синтаксис которого интуитивно понятен даже человеку с ним не знакомым.
\refstepcounter{subsubsection}
\subsubsection*{\thesubsubsection. JSON-RPC}
JSON-RPC лишь описывает протокол общения между клиентом и сервером, а всё остальное зависит от конкретной реализации, каких множество для большого числа языков программирования. Однако большинство даже самых популярных библиотек оставляют желать лучшего относительно удобства их использования: слишком многие простые операции приходится делать вручную (например, формировать сообщение-вызов удаленной функции). Причина столь низкого качества реализации в отсутствии поддержки со стороны больших IT-корпораций вроде Microsoft, Google и т.п. Также стоит отметить, что не существует кроссязыковых библиотек JSON-RPC, из чего следуют сложности и всяческие неудобства при разработке проекта на нескольких языках.

\section{Межпроцессное взаимодействие}
RPC-сервер и реализация численной модели представляют из себя совершенные разные по функциям модули. Каким образом их связать и наладить передачу данных между конечным пользователем и численной моделью?

Самый очевидный ответ - объединить модули, т.е. написать общую программу, содержащую в себе оба модуля, которые будут общаться друг с другом через банальный вызов функций языка программирования. Однако этот подход очень недальновиден. Объединяя разные по функционалу модули в один, мы лишаем систему гибкости и любое ее изменение, даже совсем небольшое, может привести чуть ли не к полному переписыванию всей системы, что неприемлимо. В качестве альтернативы предлагается использовать технологию межпроцессного взаимодействия.

Межпроцессное взаимодействие (англ. \EN{inter-process communication, IPC}) -- обмен данными между потоками одного или разных процессов. В данном случае RPC-сервер и численная модель будут представлять из себя два независимых процесса. С помощью IPC они смогут общаться друг с другом, тем самым почти друг от друга не завися. Модули могуть быть написаны даже на разных языках программирования. Необходимо лишь определить интерфейс взаимодействия.

Существует множество библиотек IPC, например, \EN{Boost.IPC, Microsoft-IPC, RabbitMQ} и другие. Однако в нашем случае функционал данных библиотек может оказаться излишним, и их использование усложнит разработку. Поэтому было решено написать простое IPC для передачи результатов численного моделирования самостоятельно. Рассмотрим, какие средства для этого предоставляет операционная система.
\subsection{Boost.Interprocess}
Интерфейс для тех или иных механизмов межпроцессного взаимодействия, естественно, предоставляет операционная система. И этот интерфейс будет представлять из себя функции языка программирования C. В таких условиях сложно написать кроссплатформенный код: придется оборачивать каждую платформо-зависимую функцию в свою, а на этапе компиляции выбирать реализацию. И тут нам пригодится еще одна библиотека Boost - Boost.Interprocess~\cite{3boost}. Эта библиотека как раз предоставляет такие обертки над интерфейсом операционной системой, представленные в виде C++-классов, что сильно упрощает дальнейшую разработку. Все описанные далее способы межпроцессного взаимодействия будут проиллюстрированы с использованием этой библиотеки.
\subsection{Общая память процессов}
Как известно, во всех наиболее распространенных операционных системах память каждого процесса изолирована от другого. Один процесс не может ни читать, ни тем более писать в память другого процесса. Это сделано прежде всего из-за соображений безопасности. Однако операционная система предоставляет механизм создания общей памяти, которой смогут пользоваться несколько процессов. Пример работы с такой памятью представлен на \cref{shared_memory}.
\begin{figure}[H]
  \lstinputlisting[language=c++]{source/shared_memory.cpp}
  \caption{Листинг. Пример работы с общей памятью процессов}
  \label{shared_memory}
\end{figure}

Однако механизм работы с общей памятью имеет множество недостатков. Во-первых, необходимо отображать общую память в память процесса, дабы она оказалось оказалось в его адресном пространстве и процесс смог получить к ней доступ (memory mapping). Во-вторых, семантика общей памяти может сильно отличаться между операционными системами, как, например, между Windows и POSIX-совместимыми системами~\cite{2ipc}. Это накладывает определенные расходы в ОС Windows для эмуляции семантики POSIX, чтобы код мог называться кроссплатформенным. В-третьих, необходимо использовать межпроцессные объекты синхронизации, что влечет за собой большие накладные расходы.
\subsection{Канал}
Другим механизмом межпроцессного взаимодействия является канал (англ. \EN{pipe}). Через канал процессы могут обмениваться данными. Семантика такова, что один процесс использует канал для вывода данных, другой же процесс для ввода. Таким образом, реализуется стратегия FIFO (First In First Out, первым зашел -- первым вышел) -- данные в канале будут прочитаны в том же порядке, в котором они туда были записаны. Так можно легко организовывать цепочки процессов (\cref{chain}), когда вывод первого будет вводом второго, вывод второго -- ввод первого и т.д. Существуют именованные и неименованные каналы.
\begin{figure}[H]
	\center{\includegraphics[width=1\linewidth]{chain_pipe}}
  \caption{Пример использования канала цепочкой процессов}
  \label{chain}
\end{figure}

Неименованный канал всегда создается для каждого процесса. Доступ к нему имеют только процесс-владелец и связанные процессые (родительский и дочерний). При завершении процесса канал закрывается и выделенные под него ресурсы освобождаются. Примером неименованного канала может послужить стандартный поток вывода программы -- stdout. Подобные каналы часто при работе в коммандной строке операционной системы Linux~\cite{2ipc}, например, когда необходимо отфильтровать результаты поиска с помощью утилиты grep или посчитать количество строк с помощью программы wc (\cref{linux}).
\begin{figure}[H]
	\center{\includegraphics[width=0.5\linewidth]{anon_pipe}}
  \caption{Пример использования неименованного канала}
  \label{linux}
\end{figure}

Именованный канал, в отличие от неименованного, может существовать отдельно от процесса и иметь отличное время жизни. Какой-либо процесс должен сначала создать такой канал и задать ему имя. Остальные процессы затем могут обращаться к нему по этому имени и производить операции записи/чтения.

\section{Разработка параллельного алгоритма Гаусса-Зейделя}
Перейдем к построению параллельного алгоритма Гаусса-Зейделя. Для того, чтобы перейти к его проектированию в смешанной системе, каковой и является кластер, необходимо построить алгоритмы для его подсистем. Начнем с последовательного алгоритма.
\subsection{Последовательный алгоритм}
Последовательный алгоритм Гаусса-Зейделя довольно прост. Последовательно проходим все ячейки матрицы со значениями $u(i,j)$ и обновляем их, вычисляя новое значение (\cref{seq}). В конце каждого такого обхода сравниваем значение дельты с необходимой точностью. Если $\delta < \epsilon$, то вычисления прекращаются. Обход матрицы организован в виде двух вложенных циклов. Весь алгоритм представляет цикл таких обходов с постусловием $delta < epsilon$. Схема алгоритма представлена на \cref{seidel_seq}.

\subsection{Параллельный алгоритм в системах с общей памятью}
В разработке параллельного алгоритма поможет такая парадигма, как векторизация. Векторизация -- вид распараллеливания программы, при котором однопоточные приложения, выполняющие одну операцию в каждый момент времени, модифицируются для выполнения нескольких однотипных операций одновременно. В данном случае речь идет о векторизации цикла: каждая итерация цикла будет выполнять не последовательно одна за другой, а одновременно.

Таким образом, алгоритм будет состоять из двух частей: цикла нарастания волны и цикла ее спада. Оба этих цикла будут векторизованы относительно текущей длины волны.

Для упрощения схемы вычисление самого значения $u(i,j)$ и дельты вынесено в отдельную функцию.

Для вычисления точности понадобилась уже не одна переменная, а целый массив размера максимальной длины волны. Это сделано с целью экономии времени на синхронизации: если бы переменная была одна, то пришлось бы синхронизировать доступ к ней. Пока один поток работает с ней, остальные обязаны просто ждать. Массив же из таких переменных позволяет конкурирующим потокам иметь свою ячейку, синхронизировать доступ к которой нет необходимости. При завершении итерации находим максимальный элемент массива (максимальную дельту) и сравниваем с требуемой точностью. Это, как и в случае последовательного алгоритма, является условием завершения вычислений. Схема алгоритма представлена на \cref{seidel_openmp1} и \cref{seidel_openmp2}.

\subsection{Параллельный алгоритм в системах\\с распределенной памятью}
Для построения алгоритма в системе с распределенной память прежде всего необходимо определить, каким образом процессоры будут распределять между собой подматрицы. Самый простой и очевидный способ -- пусть каждый отдельный блок рассчитывает отдельный процессор. Одна такой подход отвратителен с точки зрения производительности, так как большинство времени процессор будет простаивать, ожидая, пока левый и верхний соседи не завершат вычисления своей подматрицы.

Исходя из того, что максимально возможное количество одновременно работающих процессоров равно максимальной длине волны, то логичным следует предположить следующий алгоритм: каждый процессор <<движется>> сначала по горизонтали, затем по вертикали (\cref{mpi_matrix}). Следующий процессор начинает вычисления сразу после того, как предыдущий процессор, находящийся выше/правее, закончил вычисления. Такой алгоритм позволит минимизировать количество пересылок граничных строк и столбцов и задействует только то количество вычислительных ресурсов, которое действительно необходимо.

MPI предоставляет возможность получить уникальный номер процессора. Этот номер позволяет писать один и тот же код, динамически изменяющий свой поток исполнения в зависимости от номера процессора, на котором исполняется программа. Таким образом, каждый блок на каждом процессоре будет рассчитываться параллельно по волновому алгоритму.
\section{Взаимодействие суперкомпьютер-пользователь}
Исходя из описанных выше протоколов удаленного вызова процедур, для своей реализации модуля удаленного управления был выбран gRPC из-за его простоты в плане разработки, бинарной сериализации данных и, как следствие, меньшего размера передаваемых по сети данных, и из-за поддержки кроссязыковой разработки, что важно, т.к. графический клиент будет написан на другом языке программирования.

Интерфейс RPC будет довольно прост. В него будут входить следующие функции:
\begin{enumerate}
  \item Запуск вычислений.\\ Запускает расчет численной модели на кластере.\\ Входные данные: необходимые для начала вычислений параметры и константы.\\ Выходные данные: поток из пакетов чисел заданной размерности.
  \item Приостановка вычислений.\\ Приостанавливает текущие вычисления и отправляет клиенту результаты расчета модели на последней итерации.
  \item Возобновление вычислений.\\ Возобновляет ранее приостановленную задачу.
  \item Прерывание вычислений.\\ Останавливает вычисления без возможности возобновления.
\end{enumerate}
Таким образом, с помощью этого интерфейса мы сможем управлять запуском задач на кластере.
\section{Взаимодействие численная модель-сервер удаленного вызова процедур}
Прежде всего, интерфейс межпроцессного взаимодействия должен быть максимально простым для разработчки программы, рассчитывающей численную модель. Лучше всего для данной цели из ранее перечисленных способов подходит неименованный канал (anonymous pipe), который представляет из себя стандартный поток вывода на консоль. Таким образом, программа модели должна всего лишь писать в консоль результаты своих расчетов на текущий момент. Такой способ позволит в том числе отладить программу вне инфраструктуры создаваемой системы.

Прежде чем перейти к реализации собственного IPC, необходимо проработать еще один момент, а именно способ чтения из анонимного канала. Существует два возможных варианта: синхронный и асинхронный.

Синхронное чтение очень просто реализовать. Оно буквально ничем не будет отличаться от чтения из файла. Но такой способ не позволит получать данные, пока в канал производится запись. Если данные от модели приходят довольно интенсивно, такое синхронное чтение может стать узким местом системы, тормозящим всю систему.

Асинхронное чтении сложнее в реализации, но оно позволяет читать из потока, пока в него кто-то пишет, пусть и с небольшой задержкой. Это позволит минимизировать временные затраты на транспортировку данных клиенту.

\section{Межпроцессное взаимодействие}
Перейдем к непосредственной реализации собственного IPC. При работе с неименованным каналом нам пригодятся еще несколько библиотек Boost -- Boost.Process и Boost.Asio~\cite{3boost}. Рассмотрим, зачем они понадобились и что они из себя представляют.
\subsection{Boost.Process}
Интерфейс работы с каналами и процессами сильно отличается в различных операционных системах. И здесь снова возникает проблема кросспатформенности создаваемой системы. Снова обратимся к библиотеке Boost. В ее составе есть Boost.Process -- библиотека, предоставляющая кроссплатформенный интерфейс для работы с процессами и каналами. Воспользуемся ей для создания дочернего процесса (в данном случае процесс численной модели будет являться дочерним по отношению к серверу удаленного вызова процедур) и для работы с неименованным каналом (\cref{boost_process}).

\subsection{Boost.Asio}
Boost.Process может осуществлять только синхронное чтение из канала. Это означает, что пока поток не завершит запись в него, никто не сможет его прочитать. В случае с неименованным каналом стандартного вывода это означает, что мы сможем прочитать данные из него только тогда, когда модель будет полностью рассчитана. Это является большим недостатком, т.к. мы не сможем наблюдать за расчетами в реальном времени.

Альтернативой синхронному чтению является асинхронное. Оно позволяет читать из потока небольшими порциями, например, до определенного символа. Такой подход позволит получать данные о расчетах на каждом их шаге. Для осуществления такого подхода используем Boost.Asio -- библиотеку, преимущественно созданную для асинхронного сетевого взаимодействия. Однако для чтения из неименованного канала она также отлично подходит. Реализация асинхронного чтения потока вывода дочернего процесса представлена на \cref{boost_asio}.
\begin{figure}[h]
  \lstinputlisting[language=c++]{source/boost_asio.cpp}
  \caption{Листинг. Асинхронное чтение потока вывода дочернего процесса~\cite{3boost}}
  \label{boost_asio}
\end{figure}

Таким образом, было реализовано простое IPC, основанное на использовании неименованного канала, позволяющее не вникать в подробности реализации со стороны разработчика, реализующего расчет численной модели. Необходимо всего лишь знать формат вывода, чтобы RPC-сервер смог корректно разобрать все данные, получаемые от численной модели.
